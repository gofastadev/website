## The question every Go repo answers differently

Clone five Go backends and you will find five different directory trees. One puts everything in `internal/`. One has a `pkg/` folder that is really a junk drawer. One went all-in on hexagonal architecture and now has four packages named `ports`. One is a single `main.go` that grew to 4,000 lines while nobody was looking. The fifth is beautiful, and the person who structured it left the company.

This is not a Go failure, it is a Go choice. The language ships strong opinions about formatting, naming and error handling, then goes completely silent on how to arrange a web backend. `go build` does not care where your files live. The compiler is equally happy with any tree that respects package boundaries.

So every team answers the structure question themselves, usually twice. Once on day one with no information, and once eighteen months later with plenty of information and no appetite for the migration.

We think that second conversation is the one worth designing for.

## There is no official layout, not even that one

Search "golang project structure" and the top result is usually [golang-standards/project-layout](https://github.com/golang-standards/project-layout), a repository with tens of thousands of stars and a name doing a lot of heavy lifting. Be clear about what it is: a community proposal, not an official standard. It does not belong to the Go team, and Go's tech lead has [publicly asked](https://github.com/golang-standards/project-layout/issues/117) for the "golang-standards" name to be reconsidered precisely because people keep mistaking it for gospel.

The Go team's actual guidance, in the official [organizing a Go module](https://go.dev/doc/modules/layout) doc, is far more modest. Start small. Use `internal/` to hide packages you do not want imported. Add `cmd/` if you ship multiple binaries. Let structure grow out of need rather than ceremony. That is the whole thing. No blessed `services/` directory, no required depth.

So the honest starting point is that you are going to choose. In practice, backends converge on one of two shapes.

## The layered layout, organized by what code is

The layered layout groups files by technical role. All the controllers together, all the services together, all the repositories together:

```
app/
  controllers/
    article.controller.go
    user.controller.go
  services/
    article.service.go
    user.service.go
  repositories/
    article.repository.go
    user.repository.go
  models/
    article.go
    user.go
```

A request flows top to bottom. The controller parses and validates input, the service holds business rules, the repository talks to the database. Every resource takes the same path through the same layers.

The strengths are real. The structure teaches itself, so a new hire who has seen one layered backend has seen them all, and "where do database queries live?" has exactly one answer. The layer boundary is a natural testing seam: mock the repository to test the service, mock the service to test the controller. Uniformity is also enforceable, because when every resource follows the same shape a reviewer can spot a service reaching straight into the database from across the room.

The cost arrives as the project grows. Working on one feature means touching four directories, and each of them scrolls further every month. By forty resources, `services/` is a wall of files, and the ones you need today sit scattered alphabetically among thirty-six you do not care about. The code for articles exists. It is just smeared across the entire tree.

## The feature layout, organized by what code is for

The feature layout, which you will also hear called vertical slice or package by feature, flips the axis. Everything about a resource lives in one place:

```
app/
  article/
    controller.go
    service.go
    repository.go
    model.go
  user/
    controller.go
    service.go
    repository.go
    model.go
```

Now "work on articles" means opening one directory. Everything you need is adjacent and everything you do not need is elsewhere. Deleting a feature is close to `rm -rf` plus fixing a few references, which sounds minor until the day you actually have to remove something and find yourself hunting fragments through every directory in a layered tree.

This shape also suits how Go thinks. A feature directory is a package, and Go's package boundary, where lowercase identifiers stay private, becomes a real architectural wall. In a layered project `controllers` must import `services` must import `repositories`, so nearly everything ends up exported and the boundaries are convention rather than compiler-checked.

The costs mirror the layered ones. Cross-cutting questions get harder, because "show me all our database access" is now a grep rather than a directory. Shared logic between features needs a deliberate home or you grow import cycles and a junk-drawer `common` package. And uniformity depends on discipline, since nothing structural stops `article` from arranging itself completely differently from `user`.

## The trade-offs that actually decide it

Strip away the architecture-blog framing and three practical forces decide this.

**Team size and collision rate.** Feature layouts localize merge conflicts, because two people on two features touch disjoint directories. Layered layouts concentrate churn, since everyone edits `services/` and route-registration files become conflict magnets.

**Codebase size over time.** Layered scales down well and up poorly. A small layered project is wonderfully legible and a huge one is a filing cabinet sorted by paper size. Feature layouts do the reverse, scaling up well and feeling like ceremony at three resources.

**Who reads the code.** People who live in a codebase daily build a mental map and stop caring about layout. It is everyone else, meaning new hires, the on-call engineer from another team, and increasingly coding agents, who lean on structure. For them a feature layout answers "what does this system do?" straight from `ls`, while a layered one answers "how is this system built?"

Notice what is missing from that list. Performance is identical, since packages are a compile-time concept. Testability is fine either way if the seams stay clean. Correctness does not enter into it. This is an ergonomics decision, which is exactly why teams change their minds: ergonomics depend on team size and codebase size, and both of those move.

## Picking on day one

When we built the [gofasta](/blog/hello-gofasta) scaffolder we refused to pick a winner, because the honest answer depends on things you do not know yet. So the choice is a flag:

```bash
gofasta new myapp --layout layered
gofasta new myapp --layout feature
```

Both produce the same working backend, with HTTP server, database layer, migrations and auth, arranged in whichever shape you asked for. The [project structure docs](/docs/getting-started/project-structure) have the full tree of each, and [`gofasta new`](/docs/cli-reference/new/index) covers the other scaffold-time options.

What matters more is that [code generation](/docs/guides/code-generation) respects the layout. `gofasta g scaffold Article title:string body:text` generates a model, migration, repository, service, DTOs, controller, route registration, a Wire provider and tests, placed wherever *your* layout says they belong. The generators keep the structure coherent as the project grows, which is where hand-maintained layouts usually start to drift.

At three developers or fewer and under a couple dozen resources, we would default to `layered`, because self-teaching uniformity is worth more than cohesion at that scale. Past that, or if you already know the domain will sprawl, start with `feature`.

And if you get it wrong? That used to be the expensive part.

## Changing your mind is allowed

The traditional cost of a layout migration is why most teams never attempt one. Moving files is easy. Updating every import path, keeping the dependency-injection wiring intact, and reviewing a 300-file diff while feature work continues is not. So the structure decays instead. New code half-follows a new convention, old code stays put, and two years later the tree is an archaeology site.

That is the real reason gofasta treats structure as a convertible property rather than a permanent one:

```bash
gofasta refactor status    # which layout is this project, and how cleanly?
gofasta refactor feature   # convert layered -> feature
gofasta refactor layered   # convert feature -> layered
```

[`gofasta refactor`](/docs/cli-reference/refactor) rewrites the tree between the two layouts, moving files and updating packages and imports, so migration is a command and a code review rather than a quarter-long project nobody will approve. `refactor status` earns its keep on its own as a drift check, telling you which layout the project actually follows today, which after a few months of hurried merges is not always the one you started with.

Cheap conversion changes the day-one decision too. You are no longer choosing a permanent home, only a starting point. That removes most of the anxiety, and most of the meeting time, from a question that never deserved the meeting.

## The mistakes we keep seeing

A few failure modes show up in both layouts often enough to name.

**The junk-drawer `pkg/`.** A top-level `pkg/` with no admission criteria becomes where code goes when nobody wants to decide. Six months in it holds a string formatter, half an email client, and something called `helpers2`. If a package has no one-line answer to "what is this for?", leave it next to its only caller until a second caller exists.

**Premature ceremony.** Interfaces with one implementation. A `domain/` and `infrastructure/` split in a three-endpoint service. A `cmd/` tree for a project shipping one binary. Go's own guidance is to grow structure out of need, and need is observable: add the seam when the second implementation, consumer or binary actually appears. Adding it earlier does not make the project enterprise-grade, it makes every file two clicks further away.

**Mixed layouts by accretion.** The project started layered, someone added a self-contained `billing/` package during a crunch, and now there are two organizing principles and every new file is a judgment call. That is the worst of both worlds, with the predictability of neither. It is also the drift `gofasta refactor status` exists to catch while the fix is still one honest conversation and one command.

**Structure by copy-paste.** New resources get created by duplicating the last one, typos and stale imports included. That is less a layout problem than a tooling gap, and it is the specific reason we lean on generators. `gofasta g scaffold` stamps out the same shape every time, and uniformity you do not have to police is the only kind that survives deadline pressure.

## Where we landed

Structure is a tool, not a virtue. The layered layout optimizes for "how is this built?" and the feature layout for "what does this do?", and both are defensible answers held by reasonable teams. Which is precisely why the Go team never blessed either.

Compressed advice: pick the layout matching your team's size today, generate code instead of hand-placing it so the structure stays coherent, and treat the layout as revisable, because with [`gofasta refactor`](/docs/cli-reference/refactor) it genuinely is. To see both shapes without committing, run `gofasta new` twice with each `--layout` flag and diff the trees. It is a five-minute experiment, and the [quick start](/docs/getting-started/quick-start) covers the rest.
