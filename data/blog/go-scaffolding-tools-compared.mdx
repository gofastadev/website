## The scaffold is the easy part

Starting a Go backend means answering a stack of questions that have nothing to do with your product. Router. Database client. Migrations. Config. Logging. Layout. Answer them well and you have spent a week. Answer them badly and you will spend that week later, with interest.

Scaffolding tools hand you a good set of answers up front. The Go ecosystem has several, and they differ in philosophy rather than quality. We build one of them, so read this with that in mind. We have used all five, and each is the right choice for somebody.

The real axis of comparison is time. Every tool here produces a working project on day zero. The interesting question is day thirty and day three hundred, when you are adding your fourteenth resource, renaming a field referenced in nine files, or handing the codebase to an AI agent.

## gonew: the official minimum

[`gonew`](https://go.dev/blog/gonew) comes from the Go team, lives in `golang.org/x/tools`, and does one thing: it copies a template module and rewrites the module path.

```bash
go install golang.org/x/tools/cmd/gonew@latest
gonew golang.org/x/example/helloserver example.com/myserver
```

Templates are ordinary Go modules distributed through the module proxy and verified by the checksum database, so your project template gets the same supply-chain guarantees as your dependencies. The Go team calls it "an extremely limited prototype meant to provide a base from which we can gather feedback and community direction."

**Where it shines.** Teams with strong existing conventions. Encode your router, layout and logging once in a template module and `gonew` stamps out consistent services with no new tooling to learn.

**Where it stops.** Everywhere else. No flags, no feature selection, and no opinions if you do not bring your own.

## go-blueprint: pick your stack, get a repo

[go-blueprint](https://github.com/Melkeydev/go-blueprint) is the community's favorite mix-and-match scaffolder, around 8,900 GitHub stars and MIT licensed. Run `go-blueprint create`, answer a few prompts or pass `--framework`, `--driver` and `--feature`, and you get a project wired for your choices.

Breadth is the selling point: six routers (chi, Gin, Fiber, Echo, gorilla/mux, HttpRouter) and six storage options (MySQL, Postgres, SQLite, MongoDB, Redis, ScyllaDB). `--advanced` adds HTMX with Templ, Tailwind, a React frontend, Docker, GitHub Actions and WebSockets.

**Where it shines.** You already know which framework you want and need scaffolding that respects the choice.

**Where it stops.** Right after generation. go-blueprint is scaffold-only by design: no CRUD generation for new resources, no patching of existing files. Day two is entirely yours.

## Autostrada: lean, curated, yours

[Autostrada](https://autostrada.dev) is Alex Edwards' generator, from the author of *Let's Go* and *Let's Go Further*, the books that taught many of us how production Go services fit together.

It is a website rather than a CLI. You pick an application type (server-rendered web app or JSON API), a database (none, SQLite, Postgres or MySQL), a router (`http.ServeMux`, Flow, chi, gorilla/mux or HttpRouter) and a few options, then download a ZIP. Some features, including automatic HTTPS, user accounts and email, sit behind a paid tier.

The code is stdlib-first with minimal dependencies, MIT licensed, and attached to nothing at runtime.

**Where it shines.** Small to medium services where you want maximum understanding per line of code, with every abstraction earning its place.

**Where it stops.** Right after the download. There is no CLI for day two, and job queues, WebSockets, RBAC and observability are yours to add by hand.

## Grit: Go and React, batteries included

[Grit](https://gritframework.dev) is the newest tool here, started in February 2026 by Muke Johnbaptist, MIT licensed and around 160 stars. It is also the most ambitious. Where the others stop at the backend, Grit scaffolds a Go API (Gin and GORM on PostgreSQL and Redis) together with a React frontend and a generated admin panel, either as one binary with the SPA embedded or as a Turborepo monorepo with separate web, admin and API apps.

Like gofasta, it keeps working after day zero. `grit generate resource` produces the Go model, handlers, migration, TypeScript types, React hooks and an admin screen in one pass. `grit start` runs every service, `grit deploy` ships a binary over SSH to systemd behind Caddy, and the scaffold arrives with 2FA, passkeys, OAuth, background jobs, S3 storage and an MCP server already wired.

**Where it shines.** Products that need a frontend and a back office as much as an API. If your team writes React anyway, nothing else here generates a resource end to end through the UI.

**Where it stops.** The scope is the tradeoff. You get Gin, PostgreSQL and React whether or not you would have chosen them, and a large surface to learn. It is young and almost entirely one maintainer's work, releasing several versions a week. `grit upgrade` also rewrites framework-owned files in your project, though it skips any file you have edited.

## gofasta: the scaffold is where it starts

[Gofasta](https://gofasta.dev) is ours, so we will describe it the way we would want a competitor to describe us, including the parts that might put you off.

`gofasta new myapp` scaffolds roughly 80 files of plain Go: a stdlib `http.Server` behind a [chi](https://github.com/go-chi/chi) router, GORM models, [golang-migrate](https://github.com/golang-migrate/migrate) migrations, JWT auth with Casbin RBAC, `slog` logging, Swagger and Docker. `--driver` picks Postgres, MySQL, SQLite, SQL Server or ClickHouse, `--graphql` adds gqlgen alongside REST, and `--layout` chooses layered or feature-based organization. The scaffold imports our companion library as opt-out defaults: delete `pkg/auth`, `go get` your preferred JWT library, and change only the two DI files that wired it in.

What sets it apart is that the CLI stays useful afterward.

* `gofasta g scaffold Article title:string body:text` generates a model, migration, repository, service, DTOs, controller, route, Wire provider and tests.
* Modify-aware generators patch code you have already written. `g field`, `g endpoint`, `g relation` and `g rename` work idempotently, all with `--dry-run`.
* [`gofasta dev`](/docs/cli-reference/dev) brings up Docker services, applies migrations and starts hot reload.
* [`gofasta deploy`](/docs/cli-reference/deploy) ships to a plain VPS over SSH with health checks and automatic rollback.
* Every command takes `--json` and `gofasta inspect` describes your resources as structured data, because the second consumer of your CLI is now somebody's coding agent and we treat it as a [first-class consumer](/blog/agent-friendly-cli-design).

**Where it stops.** It is backend-only, and heavier than everything here except Grit. We offer one router and chose it for you. If you want a stdlib-only tree with a dozen dependencies, our scaffold will feel full. The generators are worth learning if you use them weekly and pure overhead if you never touch the CLI after `new`.

## Day two is the real test

A scaffold's value starts depreciating the moment it lands. Every commit takes the project further from the template, and within a month the scaffold is archaeology.

So ask what your next year looks like. If it is one service that grows slowly, scaffold quality matters most and any of these tools will serve you well. If it is a resource-heavy API where the team, or an agent guided by [structured CLI output](/docs/cli-reference/index), adds models weekly, tooling that survives past day zero dominates the math. A full CRUD layer by hand takes us about an hour. `g scaffold` takes seconds and produces [the code we would have written anyway](/blog/hello-gofasta).

## What they all get right

All five tools generate code and then hand it over. No runtime dependency on the generator, and no tool rewriting your code underneath you. Grit's `grit upgrade` comes closest, and even it leaves every file you have edited alone.

The ZIP from Autostrada, the module copy from `gonew`, the repo from go-blueprint, the monorepo from Grit, the 80 files from `gofasta new`: each is plain Go the moment it lands. Buildable with `go build`, debuggable with Delve, greppable by the newest person on the team.

We compete on the quality of the code we leave behind and on how much of the surrounding toil we absorb. It also means switching costs are close to nil. These tools are doors, not buildings.

## What none of them do for you

None of these tools chooses your domain model, and that is what decides whether the codebase is pleasant in a year. A scaffold answers "where does the router go." It has nothing to say about whether `Order` should own its line items, whether billing belongs in the same service, or which of your resources are really one resource wearing two names.

Nor can they enforce consistency on their own. Generated uniformity decays the moment people hand-write new resources next to generated ones.

## Which one should you pick?

Our honest routing table:

* **Your team maintains its own conventions and templates.** Use `gonew`. Official, minimal, supply-chain-verified.
* **You have already chosen your framework.** Use go-blueprint. Widest menu, biggest community.
* **You want the leanest possible codebase and you trust Alex Edwards' taste,** which you should. Use Autostrada.
* **You want the API, the React frontend and the admin panel from one command.** Use Grit.
* **You want a backend scaffold plus a CLI that keeps generating, migrating and deploying for the life of the project.** That is the job [gofasta](/docs/getting-started/quick-start) was built for.

All five produce plain Go you own outright. The cost of choosing wrong is a weekend, not a rewrite.
