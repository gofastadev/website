Most "build a REST API in Go" tutorials stop right where the real work starts. You get a router, two handlers and an in-memory map standing in for a database, and then you are on your own for migrations, error handling, concurrency, logging and deployment.

This series, *Production Go, step by step*, covers that part. By the end of this first post we will have a bookshelf API with a real database under versioned migrations, structured errors, optimistic locking, health probes, metrics and a server that shuts down cleanly. Auth gets its own post next.

I am using [Gofasta](https://gofasta.dev/docs/getting-started/introduction) to generate the boilerplate. The reason is practical: it writes plain Go files into your repository instead of giving you a runtime to build on, so we can read every layer it produces and judge it on its merits. Where it falls short, I will say so and fix it by hand.

## Scaffolding the project

```bash
go install github.com/gofastadev/cli/cmd/gofasta@latest
gofasta new github.com/you/bookshelf
cd bookshelf
```

Passing a full module path sets `go.mod` correctly; `gofasta new bookshelf` also works and uses `bookshelf` as the module name. Postgres is the default database. `--driver` switches to MySQL, SQLite, SQL Server or ClickHouse, `--graphql` adds gqlgen next to REST, and `--layout` picks between layered and feature-based folders, which I compared in [a separate post](/blog/go-project-structure-layered-vs-feature). I am keeping the defaults.

The result is about 80 files. The server is a stdlib `http.Server` with [chi](https://github.com/go-chi/chi) for routing, models are [GORM](https://gorm.io) structs, dependency injection is compile-time [Wire](https://github.com/google/wire), and logging is `slog`. Config, auth and middleware come from the Gofasta library (`pkg/config`, `pkg/auth`, `pkg/middleware`), imported like any other dependency. If you prefer a different JWT library, you delete the import and rewire the two files under `app/di/` that use it.

## Reading the tree first

Spend five minutes in the tree before generating anything:

* `app/` is the domain code: models, repositories, services, controllers, DTOs.
* `app/rest/routes/index.routes.go` mounts everything, with resource routes under `/api/v1`.
* `cmd/serve.go` builds the server and the middleware chain.
* `db/migrations/` already has a users table plus database-level triggers.
* `config.yaml` holds settings, and environment variables override it.

Every model embeds `BaseModelImpl` from `pkg/models`:

```go
type BaseModelImpl struct {
	ID            uuid.UUID
	CreatedAt     time.Time
	UpdatedAt     time.Time
	DeletedAt     gorm.DeletedAt
	RecordVersion int `gorm:"type:int;not null;default:1"`
	IsActive      bool
	IsDeletable   bool
}
```

(Tags trimmed for space.) `DeletedAt` gives soft deletes, and `RecordVersion` is the basis for optimistic locking, which we will use from curl in a minute.

## The first resource

```bash
gofasta g scaffold Book title:string author:string blurb:text pages:int
```

That writes a model, a migration pair, a repository, a service, DTOs, a controller, route registration, a Wire provider and tests for each layer. The model is what you would write by hand:

```go
// app/models/book.model.go
type Book struct {
	models.BaseModelImpl
	Title  string `gorm:"not null" json:"title"`
	Author string `gorm:"not null" json:"author"`
	Blurb  string `gorm:"type:text;not null" json:"blurb"`
	Pages  int    `gorm:"not null" json:"pages"`
}
```

The routes are registered on chi, each handler wrapped by `httputil.Handle` so it can return an error instead of writing one:

```go
r.Get("/books", httputil.Handle(c.List))
r.Post("/books", httputil.Handle(c.Create))
r.Get("/books/{id}", httputil.Handle(c.GetByID))
r.Put("/books/{id}", httputil.Handle(c.Update))
r.Delete("/books/{id}", httputil.Handle(c.Archive))
```

Note that these routes are public. Nothing generated for `Book` sits behind auth yet; [part two](/blog/jwt-authentication-rbac-go) fixes that.

Apply the migration and start the dev loop:

```bash
gofasta migrate up
gofasta dev
```

`gofasta dev` starts the Docker services, applies pending migrations and runs the server under [Air](https://github.com/air-verse/air), so a save rebuilds in about a second. The [hot reload post](/blog/go-hot-reload-dev-loop) covers what it does underneath.

## Talking to the API

Create a book. Every field in the create DTO is tagged `validate:"required"`, so all four go in the body:

```bash
curl -si localhost:8080/api/v1/books \
  -H "Content-Type: application/json" \
  -d '{"title":"The Go Programming Language","author":"Donovan & Kernighan","blurb":"The classic.","pages":380}'
```

You get `201 Created`, an `ETag: "1"` header and the record wrapped in `data`:

```json
{
  "data": {
    "id": "6f1c…",
    "recordVersion": 1,
    "createdAt": "…",
    "updatedAt": "…",
    "isActive": true,
    "isDeletable": true,
    "title": "The Go Programming Language",
    "author": "Donovan & Kernighan",
    "blurb": "The classic.",
    "pages": 380
  }
}
```

Leave `blurb` out and the validator rejects it before the service runs, with a `422` and a field-level message:

```json
{
  "error": "invalid input",
  "details": [{ "fieldName": "blurb", "message": "Blurb is a required field" }]
}
```

Listing is paginated. Defaults are page 1, ten per page, newest first:

```bash
curl -s 'localhost:8080/api/v1/books?page=1&limit=5'
```

The response carries `data` plus a `pagination` object with `totalRecords`, `recordsPerPage`, `totalPages` and `currentPage`.

## Optimistic locking over HTTP

This is the part I did not expect from a generator. Updates require an `If-Match` header carrying the version from the `ETag`:

```bash
curl -si -X PUT localhost:8080/api/v1/books/$ID \
  -H "Content-Type: application/json" \
  -H 'If-Match: "1"' \
  -d '{"pages":400}'
```

That succeeds and returns `ETag: "2"`. Send the same request again with `"1"` and you get `412 Precondition Failed`, because someone (you) already changed the row. Omit the header and you get `428 Precondition Required`. `If-Match: *` skips the check deliberately.

Two clients editing the same book can no longer overwrite each other silently. The update DTO uses pointer fields with `omitempty`, so a partial body like `{"pages":400}` only touches `pages`.

## How a request moves through the layers

Controller, then service, then repository. Here is the generated `Create` handler, unedited:

```go
func (c *BookController) Create(w http.ResponseWriter, r *http.Request) error {
	in, err := httputil.DecodeJSON[dtos.TCreateBookDto](r)
	if err != nil {
		return apperrors.NewBadRequest("invalid request body", nil)
	}
	if errs := c.validator.ValidateStruct(in); len(errs) > 0 {
		return apperrors.NewValidation("invalid input", errs)
	}
	entity, err := c.svc.Create(r.Context(), in.ToCreateInput())
	if err != nil {
		return apperrors.NewInternal("failed to create book", err)
	}
	w.Header().Set("ETag", bookRecordVersionETag(entity.RecordVersion))
	return httputil.Created(w, dtos.TBookResponseDto{Data: dtos.BookFromModel(entity)})
}
```

The handler never writes a status code for errors. It returns a typed `pkg/errors` value and `httputil.Handle` maps it: validation to 422, not found to 404, conflict to 409, internal to 500. A 500 is logged with its cause, while the response body only carries the message, so internal details do not leak to clients.

The repository passes the request context into every query:

```go
if err := r.db.WithContext(ctx).Create(entity).Error; err != nil {
	span.RecordError(err)
	return fmt.Errorf("BookRepository.Create: %w", err)
}
```

If the client disconnects, the query is cancelled instead of holding a connection. Each repository method also opens an OpenTelemetry span, which costs nothing until you turn tracing on.

## The production checklist

Here is what I check before calling an API production-ready, and where this one stands.

**Middleware.** `buildMiddlewareChain` in `cmd/serve.go` is short enough to read in full:

```go
middlewares := []middleware.Middleware{
	middleware.RequestID(),
	middleware.RequestLogging(logger),
	middleware.Middleware(devtools.Recovery(middleware.Recovery(logger))),
	middleware.CORS(cfg.Server.AllowedOrigins),
	middleware.SecurityHeaders(cfg.Security),
	middleware.Middleware(devtools.Middleware),
}
if cfg.RateLimit.Enabled {
	middlewares = append(middlewares, middleware.RateLimit(cfg.RateLimit))
}
```

The devtools wrappers are no-ops in production builds. Panic recovery is the one you cannot skip: a nil dereference in one handler should not take the process down.

**Rate limiting and CORS.** Both are configured in `config.yaml`:

```yaml
server:
  allowed_origins:
    - "http://localhost:3000"

rate_limit:
  enabled: true
  rate: "100-S"     # 100 requests per second per client
  store: memory     # memory or redis
```

Two things to change before deploying. Set your real frontend origin. And if you run more than one instance, switch `store` to `redis`, otherwise each instance counts separately and the effective limit multiplies.

**Health probes.** `/health`, `/health/live` and `/health/ready` are mounted at the root. Readiness checks the database and cache, so a load balancer or Kubernetes can use it directly.

**Metrics and tracing.** Prometheus metrics are on by default at `/metrics`. Tracing is off:

```yaml
observability:
  metrics_enabled: true
  tracing_enabled: false
  metrics_path: /metrics
```

Flip `tracing_enabled` once you have a collector, and the repository spans start flowing.

**API docs.** `gofasta swagger` builds an OpenAPI spec from the annotations on each controller method.

## Graceful shutdown, and the timeouts you need to add

**Shutdown is handled.** `cmd/serve.go` waits for SIGTERM, stops the scheduler and job queue, then drains in-flight requests:

```go
shutdownCtx, cancel := context.WithTimeout(context.Background(), cfg.Server.ShutdownTimeout)
defer cancel()

if err := srv.Shutdown(shutdownCtx); err != nil {
	slog.Error("server forced to shutdown", "error", err)
}
```

The window is `server.shutdown_timeout: 15s` in `config.yaml`.

**Server timeouts are not set.** The generated server is only this:

```go
srv := &http.Server{
	Addr:    cfg.Server.Host + ":" + cfg.Server.Port,
	Handler: rootHandler,
}
```

With Go's defaults there is no read or write deadline, so one slow client can hold a connection open indefinitely, and enough of them exhaust file descriptors. This is the first edit I make:

```go
srv := &http.Server{
	Addr:              cfg.Server.Host + ":" + cfg.Server.Port,
	Handler:           rootHandler,
	ReadHeaderTimeout: 5 * time.Second,
	ReadTimeout:       15 * time.Second,
	WriteTimeout:      30 * time.Second,
	IdleTimeout:       60 * time.Second,
}
```

Tune the numbers to your endpoints. `WriteTimeout` also caps streaming responses, so the `/ws` WebSocket route or a long download needs its own handling. For outbound calls, give every HTTP client a timeout, because `http.DefaultClient` waits forever.

## Tests

Every generated layer comes with tests, run by `gofasta test` (add `--coverage` for the number). They cover the CRUD path; treat them as a starting point.

For repository tests I want a real database. `testdb.SetupTestDB` starts a throwaway Postgres container with [testcontainers-go](https://golang.testcontainers.org) and cleans it up afterwards. It only installs the shared trigger functions, not your migrations, so the test creates its own table:

```go
package repositories_test

import (
	"context"
	"testing"

	"github.com/gofastadev/gofasta/pkg/testutil/testdb"

	"github.com/you/bookshelf/app/models"
	"github.com/you/bookshelf/app/repositories"
)

func TestBookRepository_CreateAndFind(t *testing.T) {
	db := testdb.SetupTestDB(t)
	if err := db.AutoMigrate(&models.Book{}); err != nil {
		t.Fatal(err)
	}
	repo := repositories.NewBookRepository(db)
	ctx := context.Background()

	book := &models.Book{Title: "Learning Go", Author: "Jon Bodner", Blurb: "Idiomatic Go.", Pages: 494}
	if err := repo.Create(ctx, book); err != nil {
		t.Fatal(err)
	}

	got, err := repo.FindByID(ctx, book.ID)
	if err != nil {
		t.Fatal(err)
	}
	if got.Title != book.Title || got.RecordVersion != 1 {
		t.Fatalf("unexpected book: %+v", got)
	}
}
```

Docker has to be running for this one. The [testing guide](https://gofasta.dev/docs/guides/testing) covers the rest.

## Changing the API later

The usual problem with generators shows up in month three: the generated code has been edited by hand, and requirements change. Gofasta's answer is generators that patch existing Go code through the AST instead of re-rendering it:

```bash
gofasta g field Book subtitle:string --dry-run
```

`--dry-run` prints what would change. Without it, the field is added to the model and DTOs and a migration is generated, while your hand edits stay put. `g endpoint`, `g relation` and `g rename` work the same way. `gofasta inspect Book` prints the resource's fields, endpoints and relations, which is useful before a refactor. The [code generation guide](https://gofasta.dev/docs/guides/code-generation) lists the rest.

## Where we ended up

About fifteen minutes of work, plus one hand edit for timeouts, gets you versioned migrations, optimistic locking enforced over HTTP, typed errors, validation, rate limiting, health probes, metrics, tests and graceful shutdown. Every piece is plain Go in your repository, so when something breaks at 2am you are reading your own code.

The [Quick Start](https://gofasta.dev/docs/getting-started/quick-start) condenses the setup, and the [REST API guide](https://gofasta.dev/docs/guides/rest-api) goes deeper on request handling.
