## Why one server is enough for a while

`go build` gives you one static binary. No runtime to install, no interpreter to match, no dependency folder to sync. A small VPS will push thousands of requests per second through that binary, and plenty of products never outgrow one box. Managed platforms buy real things, like nobody paging you about disks. But a few dollars a month against a bill that scales with your traffic deserves a fair hearing first.

This is part 4 of *Production Go, step by step*. We [built the API](/blog/build-production-rest-api-go), [added auth](/blog/jwt-authentication-rbac-go), and [versioned the schema](/blog/database-migrations-go). Now we ship it, using the deploy command that comes with the Gofasta CLI.

A deploy process has to answer four questions, and a three-line `scp` script answers none of them:

* Did the new version actually come up?
* What is running right now?
* How do I get back to the last good release, quickly?
* What did the app log before it fell over?

## Configuring the deploy

Everything lives in the `deploy:` section of `config.yaml`:

```yaml
deploy:
  host: ""              # user@server.com (required for gofasta deploy)
  method: docker        # docker or binary
  port: 22              # SSH port
  path: ""              # remote directory (default: /opt/bookshelf)
  arch: amd64           # target architecture: amd64 or arm64
  health_path: /health/ready
  health_timeout: 30    # seconds to wait for health check
  keep_releases: 3      # number of old releases to keep for rollback
  strict_host_key: accept-new
  domain: ""
```

I set `host: deploy@203.0.113.10` and `domain: api.bookshelf.dev` and left the rest alone. Every value can be overridden with a flag (`--host`, `--method`, `--port`, `--path`, `--arch`), and `--dry-run` works on every subcommand. It prints the SSH commands without running them, which is the best way to learn what the tool actually does.

## Preparing the server once

You need key-based SSH access to a fresh Debian or Ubuntu box. Setup runs `apt-get`, so other distros are out for now. Then:

```bash
gofasta deploy setup
```

It runs five steps over plain SSH, with no agent left on the server:

1. Tests SSH connectivity.
2. Installs `curl` and `nginx`.
3. Installs Docker via `get.docker.com` and adds your user to the `docker` group. For `--method binary`, it creates a service user and installs the `migrate` CLI instead.
4. Creates `/opt/bookshelf/releases` and `/opt/bookshelf/shared`.
5. If `deploy.domain` is set, uploads `deployments/nginx/app.conf` with your domain filled in and reloads nginx.

Two things to do by hand afterwards. Log out and back in so the Docker group membership applies, as setup warns you. Then put your production secrets on the server:

```bash
ssh deploy@203.0.113.10 'cat > /opt/bookshelf/shared/.env' < .env.production
```

The production compose file refuses to start without them. It uses compose's `:?` syntax so a missing secret fails loudly instead of booting a broken app:

```yaml
- BOOKSHELF_AUTH_JWT_SECRET=${BOOKSHELF_AUTH_JWT_SECRET:?missing — set in the deploy host's .env}
```

## The deploy itself

```bash
gofasta deploy --dry-run   # read the plan first
gofasta deploy
```

With the default Docker method, this runs eleven steps:

1. Checks `ssh`, `scp` and local Docker, then remote `docker` and `docker compose`.
2. Builds the image locally, tagged with a UTC timestamp such as `bookshelf:20261107-143022`.
3. Creates the release directory.
4. Streams the image with `docker save | ssh docker load`. Nothing is built on the server.
5. Uploads `.env` and `config.yaml` to `shared/` and links them into the release.
6. Copies `deployments/docker/compose.production.yaml` in as `compose.yaml` and writes the image tag to a `RELEASE_IMAGE` file.
7. Records the current release so it has somewhere to roll back to.
8. Cuts over: `docker compose up -d` on a fixed project name with the new image pinned, then moves the `current` symlink.
9. Runs `/app migrate up` inside the new container.
10. Polls the health endpoint.
11. Prunes releases beyond `keep_releases`, along with their images.

The server ends up looking like this:

```text
/opt/bookshelf/
├── current -> releases/20261107-143022
├── releases/
│   ├── 20261105-091500/   compose.yaml, RELEASE_IMAGE, .env -> ../../shared/.env
│   └── 20261107-143022/
└── shared/
    ├── .env
    └── config.yaml
```

Know what you are getting: this is a **restart, not a zero-downtime deploy**. The app container is replaced in place, so expect a blip of a few seconds. The fixed compose project name keeps the database container and its volume untouched across releases.

## The health gate and automatic rollback

Step 10 runs a probe from inside the app container:

```bash
docker compose -p bookshelf -f compose.yaml exec -T app wget -qO /dev/null http://127.0.0.1:8080/health/ready
```

It retries every two seconds for `health_timeout` seconds. `/health/ready` is the right target because it checks the database and cache. Plain `/health` answers 200 as soon as the process is up, even when Postgres is unreachable.

If the cutover, the migration or the probe fails, the CLI restarts the previous release's pinned image, moves `current` back, health-checks that too, and deletes the failed release so a later rollback cannot land on it. Two caveats from reading the source:

* **The first deploy has nothing to roll back to.** A broken first release is left running so you can inspect it.
* **Migrations are not reverted.** With the Docker method, migrations run after the cutover, and a rollback restores the old code, not the old schema. Every migration therefore has to work with the previous release too: add columns before using them, drop them a release later. [Part 3](/blog/database-migrations-go) covers this expand-then-contract pattern. The binary method runs migrations before the cutover and leaves the running service untouched if they fail.

## Day two

```bash
gofasta deploy status     # readlink current + docker compose ps
gofasta deploy logs       # docker compose logs -f --tail 100
gofasta deploy rollback   # back to the newest release older than current
```

`rollback` exists for failures a probe cannot see, like a release that boots fine and calculates every invoice wrong. It picks the target by timestamp, starts it, health-checks it, and puts the current release back if the target turns out unhealthy too. Every command except `logs` also accepts `--json`, which is handy in scripts.

## Three things I changed before going live

Reading the CLI source turned up three traps.

**1. Deploying from a laptop can overwrite production secrets.** Step 5 uploads the `.env` in your working directory to `shared/.env` whenever one exists. Your local `.env` holds development values, so a deploy from your machine replaces the production file. CI checkouts have no `.env` (it is gitignored), so the server copy survives there. My rule: production deploys only run from CI.

**2. The app port is public.** The production compose file publishes `"${PORT:-8080}:8080"`, which binds every interface. Docker writes its own iptables rules, so `ufw` will not block it. Anyone can skip nginx and hit `:8080` directly. I bind it to loopback in `deployments/docker/compose.production.yaml`:

```yaml
ports:
  - "127.0.0.1:${PORT:-8080}:8080"
```

**3. CI deploys do not wait for tests.** The scaffold ships workflows under `deployments/ci/`, but `Test` and `Deploy to VPS` both trigger on push to `main`, independently. After copying them into `.github/workflows/`, I made the deploy depend on the test run:

```yaml
on:
  workflow_run:
    workflows: ["Test"]
    types: [completed]
    branches: [main]

jobs:
  deploy:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
```

The deploy workflow already has a `concurrency` group with `cancel-in-progress: false`, so two merges queue instead of racing.

## TLS

Setup installed the nginx vhost, which proxies to `127.0.0.1:8080` and forwards `X-Forwarded-*` and `X-Request-ID`. Certificates are left to you, and setup prints the two commands:

```bash
sudo apt-get install -y certbot python3-certbot-nginx
sudo certbot --nginx -d api.bookshelf.dev
```

Then uncomment the `return 301 https://...` line in the vhost. Sessions already expect HTTPS: production compose sets `SESSION_COOKIE_SECURE=true`.

## The binary method

If you would rather skip Docker, `gofasta deploy --method binary` cross-compiles with `CGO_ENABLED=0`, uploads the binary plus `migrations/`, `templates/` and `configs/`, and runs it under the systemd unit in `deployments/systemd/app.service`. That unit runs as a dedicated user with `NoNewPrivileges`, `ProtectSystem=strict` and `PrivateTmp`. Logs go to `journalctl`, and `deploy logs` tails them. The database is then yours to run, since nothing provisions Postgres on the host.

## What one VPS does not solve

* **One server is one failure domain.** Rollback protects you from bad releases, not dead hosts.
* **Backups are on you.** The release directories hold binaries and images, not data. Schedule `pg_dump` off the box into object storage, and test a restore once.
* **Scale ceilings are real.** When one machine is not enough, a load balancer and a managed database stop being overhead.

If you want single-server economics with a UI on top, [Coolify, Dokploy and Kamal](/docs/guides/deployment) all run a Gofasta project as-is, since it is plain Go plus Docker.
