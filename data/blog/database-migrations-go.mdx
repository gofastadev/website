## The schema outlives the code

You can rewrite a service, rename packages or delete a whole layer, and the compiler and tests will catch you. The database is different. The `users` table you create this week will still hold real data in five years, and every change between now and then happens in place, on a live system.

This is part 3 of *Production Go, step by step*. Part 1 [built the bookshelf API](/blog/build-production-rest-api-go) and part 2 [added authentication](/blog/jwt-authentication-rbac-go). This time we look at the SQL underneath: the migration files Gofasta generates, the triggers it puts in the database, and how to change a live schema without breaking the running app.

## Why not AutoMigrate

GORM's `AutoMigrate` diffs your structs against the live schema and adds tables and columns until they match. For a prototype it is fine. For production it has four problems:

* It never drops columns, so a rename quietly leaves you with two.
* It has no ordering, so two environments can end up with the same shape but different histories.
* There is no down path, so there is no rollback.
* It leaves no record of what changed or when.

Production needs answers to "what exactly will change, in what order, and how do I undo it?" Versioned SQL files answer that, and that is what the scaffold uses.

## What the CLI wraps

`gofasta migrate` shells out to [golang-migrate](https://github.com/golang-migrate/migrate) and builds the database URL from `config.yaml`, so you need the `migrate` binary on your `PATH` (`gofasta doctor` checks for it). The files are plain golang-migrate format, so if you stop using Gofasta they still run with `migrate` on its own.

The day-to-day commands:

```bash
gofasta migrate up             # apply everything pending
gofasta migrate down           # interactive menu: one step, N steps, or all
gofasta migrate down --steps 1 # scripted, no prompt
gofasta db reset               # drop everything, re-migrate, re-seed (dev only)
```

In CI or with piped stdin, `migrate down` without flags rolls back one step instead of waiting on the menu. `--all` asks for confirmation unless you pass `--yes`.

## What a new project starts with

`gofasta new bookshelf` defaults to Postgres and copies five foundational migrations into `db/migrations/`:

```text
000001_create_citext_extension.up.sql
000002_create_function_to_update_updated_at_column.up.sql
000003_create_function_to_avoid_deleting_not_deletable_record.up.sql
000004_increment_record_version.up.sql
000005_create_users.up.sql
```

Each has a matching `.down.sql`. Migrations 2 to 4 define shared PL/pgSQL functions that every table's triggers call. Here is the version counter:

```sql
CREATE OR REPLACE FUNCTION increment_record_version_column_function() RETURNS TRIGGER AS $$
BEGIN
    NEW.record_version := OLD.record_version + 1;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

The other drivers each get a single `000001_create_users` migration written for that engine. On MySQL, `updated_at` uses `ON UPDATE CURRENT_TIMESTAMP` and the other two rules are per-table triggers. SQLite uses `AFTER UPDATE` triggers that update the row again, plus a guarded delete trigger:

```sql
CREATE TRIGGER avoid_deleting_not_deletable_users_trigger
    BEFORE DELETE ON "users"
    FOR EACH ROW WHEN OLD.is_deletable = 0
BEGIN
    SELECT RAISE(ABORT, 'This record is not deletable');
END;
```

SQL Server wraps each `CREATE TRIGGER` in `EXEC sp_executesql N'...'`, because golang-migrate sends the whole file as one batch and T-SQL requires `CREATE TRIGGER` to be the only statement in its batch. That is the kind of detail I am glad someone else worked out.

One thing I noticed in the Postgres set: migration 1 enables `citext`, but `users.email` is declared as plain `character varying`, so uniqueness is case-sensitive out of the box. If you want `Alice@x.com` and `alice@x.com` treated as the same account, change the column to `citext` in your own migration or lowercase emails before saving them.

## Generating a table

When you run `gofasta g scaffold Book ...`, the migration comes with the rest of the resource. If you only want the SQL, `g migration` takes the same resource and field arguments:

```bash
gofasta g migration Book title:string author:string blurb:text pages:int
```

Files are numbered sequentially from the highest one in the folder, so this writes `000006_create_books.up.sql`:

```sql
CREATE TABLE IF NOT EXISTS books (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title VARCHAR(255) NOT NULL,
    author VARCHAR(255) NOT NULL,
    blurb TEXT NOT NULL,
    pages INTEGER NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT true,
    is_deletable BOOLEAN NOT NULL DEFAULT true,
    record_version INT NOT NULL DEFAULT 1,
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    updated_at TIMESTAMP NOT NULL DEFAULT now(),
    deleted_at TIMESTAMP
);

CREATE TRIGGER increment_record_version_column_function_on_books_trigger
    BEFORE UPDATE ON books
    FOR EACH ROW EXECUTE FUNCTION increment_record_version_column_function();
```

(The real file also attaches the `updated_at` and not-deletable triggers.) The down file drops the three triggers, then the table. Column types follow `database.driver` in `config.yaml`: `float` becomes `DECIMAL(10,2)` on Postgres and MySQL, and `string` becomes `NVARCHAR(255)` on SQL Server.

A caveat: `g migration` always produces a `CREATE TABLE`. Its help text says it is useful for indexes and constraints, but `gofasta g migration add_status_to_books` gives you `000006_create_add_status_to_bookses.up.sql` with a table by that name. For anything that is not a new table, create the pair by hand with the next number.

## Adding a column

For columns on an existing resource, `g field` writes an `ALTER` migration and patches the model and DTOs in the same step:

```bash
gofasta g field Book subtitle:string --dry-run
```

The migration it writes, `000007_add_subtitle_to_books.up.sql`:

```sql
ALTER TABLE books ADD COLUMN subtitle VARCHAR(255) NOT NULL DEFAULT '';
```

The `DEFAULT ''` matters. A `NOT NULL` column without a default cannot be added to a table that already has rows, so the generator adds a zero value for strings and numbers. The down file is `ALTER TABLE books DROP COLUMN subtitle;`.

## Invariants the database enforces

Every model embeds `BaseModelImpl`, which carries `UpdatedAt`, `RecordVersion` and `IsDeletable`. The application keeps them correct, but the application is not the only client. There is `psql`, someone's GUI tool, a one-off data-fix script, and in the worst case someone who found a connection string. The triggers keep three rules true for all of them:

* `updated_at` changes on every UPDATE.
* `record_version` increments on every UPDATE.
* Rows with `is_deletable = false` cannot be hard-deleted.

The generated repository adds an optimistic lock on top. `UpdateIfVersionMatches` puts the version in the WHERE clause, so a stale write affects zero rows and you can return a clean conflict:

```go
fields["record_version"] = version + 1
res := tx.Model(&models.Book{}).
	Where("id = ? AND record_version = ?", id, version).
	Updates(fields)
```

Two gaps are worth knowing about. First, ClickHouse has no row-level triggers, so on that driver all three rules hold only in application code. The scaffold's migration says so in a comment. Second, the delete guard covers hard `DELETE` only. The app's own deletes are soft deletes, an `UPDATE` that sets `deleted_at`, and `SoftDeleteIfDeletable` checks `is_deletable` in Go. A raw `UPDATE books SET deleted_at = now()` from `psql` will soft-delete a protected row. If that matters for your data, add a `BEFORE UPDATE` trigger that rejects setting `deleted_at` when `is_deletable` is false.

## A safe rename: expand, then contract

Say `blurb` should become `summary`. A single `RENAME COLUMN` breaks any running instance still reading `blurb` for as long as old and new versions overlap during a deploy. The safe version takes three releases.

**Release 1, expand.** Add the new column, then have the app write to both and backfill:

```sql
-- 000008_add_summary_to_books.up.sql
ALTER TABLE books ADD COLUMN summary TEXT NOT NULL DEFAULT '';
UPDATE books SET summary = blurb;
```

**Release 2, switch reads.** The code reads `summary` and stops writing `blurb`. No migration.

**Release 3, contract.** Drop the old column:

```sql
-- 000009_drop_blurb_from_books.up.sql
ALTER TABLE books DROP COLUMN blurb;
```

Before shipping, `migrate up --explain` statically checks every `.up.sql` without touching a database. On a branch that also had a naive rename and a new index, it printed (trimmed):

```text
  000008  rename_blurb
    risk: app-incompatibility
    · ALTER TABLE books RENAME COLUMN blurb TO summary;
      [medium] RenameColumn — RENAME COLUMN breaks running app versions that still read the old name; two-phase the rename (add new, dual-write, switch reads, drop old)

  000009  contract_books_blurb
    risk: data-loss
    · ALTER TABLE books DROP COLUMN blurb;
      [high] DropColumn — DROP COLUMN permanently removes data; backfill or two-phase deploy if the column is still read by any running app version

Summary: max-risk=data-loss · 1 high · 2 medium · 0 low
```

Add `--strict` in CI and the command exits non-zero on any high-severity finding. It also flags a plain `CREATE INDEX` because it locks writes on Postgres. If you switch to `CREATE INDEX CONCURRENTLY`, put it in its own migration file: Postgres runs a multi-statement file as one implicit transaction, and `CONCURRENTLY` refuses to run inside one.

## When a migration fails halfway

If a migration dies mid-file, golang-migrate marks the version *dirty* and refuses to go further, because it cannot know how much of the DDL committed. `gofasta migrate repair` does not run any SQL. You reconcile the database by hand first, then tell it which state you reached:

```bash
gofasta migrate repair --revert    # you undid the partial change: mark N-1 current
gofasta migrate repair --complete  # you finished it by hand: mark N current
```

There is also `--force N` to set the version directly. Without flags in a non-interactive shell, it refuses to guess and exits non-zero, which is what you want in automation.

## Habits that prevent most incidents

* **One change per migration.** A failing "add orders index" is debuggable. A failing "restructure billing" is not.
* **Never edit an applied migration.** Once it has run outside your laptop, fix forward with a new file. Otherwise databases that ran the old version and ones that ran the new version disagree forever while the tracking table says they match.
* **Keep data out of schema migrations.** Rows go in seeds. `gofasta seed` runs the registered seeders, and `seed --fresh` drops, re-migrates and seeds.
* **Review the down file.** It is the code you will run at your worst moment.

## Keeping it boring

`gofasta dev` runs `migrate up` once your services are healthy, so a teammate's migration is just there after a pull. CI and production run the same files, and `git log db/migrations/` is the schema's full history. The [database guide](/docs/guides/database-and-migrations) and the [migrate reference](/docs/cli-reference/migrate) cover the rest.
