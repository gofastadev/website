## The schema outlives everything

Code is replaceable. We rewrite services, rename packages, and delete whole layers without much ceremony, because the compiler and the test suite have our backs. The database is different. The `users` table you create this week will still be holding real people's data in five years, and every change you make to it between now and then has to happen in place, on a live system, without losing a row.

That's why we think migrations are the least skippable part of a Go backend, and why they're worth doing with plain SQL files instead of something cleverer. This post covers how gofasta handles them: what the CLI actually wraps, what a fresh scaffold ships for each supported database, and the part we think is genuinely underrated — the invariants the database enforces on its own, no matter which client is talking to it.

This is part 3 of *Production Go, step by step*. Part 1 [built the API](/blog/build-production-rest-api-go); part 2 [put authentication in front of it](/blog/jwt-authentication-rbac-go). Today we go below the ORM.

## The honest section about auto-migrate

GORM ships an `AutoMigrate` function, and if you've prototyped in Go you've probably used it: point it at your structs and it diffs them against the live schema, creating tables and adding columns until the two agree. For a spike or a weekend project it's great. We use it that way ourselves.

Here's what it doesn't do, and by design can't. It never drops a column, so a rename quietly becomes two columns. It has no ordering, so two environments that ran different builds end up with schemas that agree in shape but not in history. It has no down path, so there is no rollback story at all. And it leaves no record of what changed when, which means debugging a production schema turns into archaeology instead of `git log`.

None of that is a bug. Auto-migration answers the question "make the database match my structs, I don't care how." Production needs the opposite question answered: "what exactly will change, in what order, and how do we undo it?" Those are different tools. Pretending one can be the other is how you end up reconstructing schema history from an old `pg_dump` at midnight.

So gofasta scaffolds don't auto-migrate. They ship versioned SQL files, applied in order, tracked in a table. The boring thing.

## Plain SQL, applied in order

We didn't reinvent migration tracking either. The `gofasta migrate` commands shell out to [golang-migrate](https://github.com/golang-migrate/migrate), the closest thing the Go ecosystem has to a standard, with connection details read from your project's `config.yaml` so you're not juggling flags or environment variables. The CLI is a thin wrapper on purpose: if you ever drop gofasta, your migrations still run with the `migrate` binary alone, because they were always just its file format.

Every migration is a pair of files. The up file moves the schema forward; the down file undoes it:

```sql
-- 20260831_add_status_to_articles.up.sql
ALTER TABLE articles ADD COLUMN status VARCHAR(50) NOT NULL DEFAULT 'draft';

-- 20260831_add_status_to_articles.down.sql
ALTER TABLE articles DROP COLUMN status;
```

Writing the down file feels like busywork right up until the moment it doesn't. A migration that can't be reversed is a one-way door, and you want to know a door is one-way *before* you walk through it, preferably in code review.

The day-to-day loop is three commands:

```bash
gofasta migrate up      # apply everything pending
gofasta migrate down    # step back
gofasta db reset        # drop it all and rebuild from zero (development only, obviously)
```

And one command for the bad day: when a migration fails halfway, golang-migrate marks the database *dirty* and refuses to touch it again — the right default, since it can't know how much of your DDL actually committed. You fix the underlying problem, then run `gofasta migrate repair` to clear the dirty flag and get back to a known version. The [migrate reference](/docs/cli-reference/migrate) covers the full flow.

New migrations come from the generator, so nobody hand-types timestamps:

```bash
gofasta g migration add_status_to_articles
```

And when you scaffold a whole resource with `gofasta g scaffold`, the migration pair arrives together with the model, repository, service, and controller — one command, every layer, including this one.

## Five databases, one workflow

Here's where it gets more interesting than the average migrations post. `gofasta new` takes a `--driver` flag: `postgres` (the default), `mysql`, `sqlite`, `sqlserver`, or `clickhouse`. That flag doesn't just swap a connection string. The CLI carries a separate set of foundational migrations for every driver and copies the matching set into your new project's `db/migrations/` at scaffold time.

A Postgres project starts with five migrations: one enables `citext` for case-insensitive text, three define shared PL/pgSQL functions, and the last creates the `users` table wired up to those functions. A MySQL project gets a single migration with its logic inlined, because MySQL has no equivalent of shared trigger functions worth the ceremony. SQLite, SQL Server, and ClickHouse each get their own variant, written for what that engine can actually do rather than translated word-for-word from the Postgres version.

The generators follow the same rule. Declare a field as `price:float` and the emitted migration says `DECIMAL(10,2)` on Postgres and the appropriate type on each of the other engines, keyed off the `database.driver` value in `config.yaml`. You write the field list once; the SQL dialect is the toolkit's problem. The [driver reference](/docs/cli-reference/new/driver) has the full type table.

Why bother supporting five engines? Because real projects don't get to choose. The startup is on Postgres, the enterprise customer mandates SQL Server, the analytics pipeline wants ClickHouse, and the CLI you use to move a schema forward shouldn't be the reason any of those conversations is hard.

## The invariants your database enforces on its own

This is the part we'd point at if someone asked why the scaffold bothers shipping triggers at all.

Every gofasta model embeds a base model carrying `UpdatedAt`, `RecordVersion`, and `IsDeletable` alongside the usual ID and timestamps. Application code maintains those fields — GORM hooks and repository methods do the right thing on every write. But your application is not the only client your database will ever have. There's `psql`. There's the GUI tool someone on the team swears by. There's the late-night data-fix script, the BI integration with a read-write credential it shouldn't have, and — worst case — an intruder who found a connection string.

So the foundational migrations push three invariants into the database itself:

* **`updated_at` always moves.** Any UPDATE from any client refreshes the timestamp, so "when did this row last change" stays answerable forever.
* **`record_version` always increments.** Every UPDATE bumps the version counter, whether or not the writer bothered to.
* **Protected rows stay put.** Rows flagged not-deletable can't be deleted, even by a client that never heard of your application layer.

How each engine gets there differs, and we think the differences are worth knowing. Postgres routes per-table triggers through those shared PL/pgSQL functions, so the logic lives in one place. MySQL handles `updated_at` with a column attribute and covers the other two with per-table triggers. SQLite does all three with `AFTER UPDATE` and `BEFORE DELETE ... WHEN` triggers. SQL Server combines the update work into one `AFTER UPDATE` trigger and blocks deletion with an `INSTEAD OF DELETE` trigger, which is the idiomatic way to veto a delete there.

ClickHouse gets none of this, and the scaffold is honest about it: its engine has no row-level triggers, so on ClickHouse the invariants hold only at the application layer. We'd rather tell you that plainly than generate SQL that pretends.

One more layer stacks on top. The generated repository's update method puts `record_version` into the WHERE clause — the classic optimistic lock — so a stale write is rejected *before* it reaches the database, with a clean conflict error you can surface to the user. The trigger is the backstop behind it: even if some other client writes around the repository entirely, the version still moves forward. The lock catches honest races; the trigger catches everything else.

That's defense in depth, and it's the kind of thing that's tedious to hand-write for one engine, let alone five — which is exactly why it belongs in a scaffold.

## Rules we follow when writing migrations

The tooling above makes migrations cheap to run. It can't make a bad migration good, so here are the habits we hold ourselves to — none of them original, all of them earned.

**Expand, then contract.** The dangerous migrations are the ones that change something the running application still depends on. Renaming a column in one step means there's a moment where old code queries a name that no longer exists. The safe sequence takes three deploys: add the new column and write to both, move all readers over, then drop the old column once nothing touches it. More steps, zero moments of disagreement between code and schema. It feels slow exactly once; after that it feels like sleep.

**Keep migrations small and single-purpose.** One logical change per pair of files. When migration 47 fails in staging, "add the orders index" is a thing you can reason about; "restructure billing" is not. Small migrations also make the down files honest — a fifty-line up file rarely has a down file anyone believes.

**Never edit an applied migration.** Once a migration has run anywhere beyond your laptop, it's history, and history is append-only. Fixing a mistake means writing a new migration that corrects it. Editing the old file just guarantees that databases which already applied it and databases which haven't will disagree forever, while the tracking table swears they're identical.

**Separate schema from data.** DDL belongs in migrations. Rows belong in seeds — `gofasta seed` runs the project's registered seeders, and `--fresh` rebuilds from a clean slate. Mixing the two means you can't rebuild a schema without also deciding what data belongs in it, which is two questions pretending to be one.

**Review migrations harder than code.** A bad function ships, breaks, gets reverted, and is forgotten by Thursday. A bad migration that drops the wrong column is not an oops; it's an incident with a restore step. The down file deserves review too — it's the code path you'll be running at your worst moment.

## Make it boring

The whole point of this machinery is that schema change stops being an event. `gofasta dev` applies pending migrations when it brings your local stack up, so a teammate's new migration is just there after a pull. CI runs the same files. Production runs the same files. One `git log db/migrations/` tells you the entire history of your schema, in order, with authorship — which is more than most teams can say about their database.

The [database guide](/docs/guides/database-and-migrations) walks through the full workflow against a fresh project if you want to try it end to end. Schemas outlive code. Treat yours like it.
